# Provisioning queue and payment-provider extensions

> Current payment flow, state transitions, price snapshots, callbacks, and currency configuration are defined in [PAYMENT-ARCHITECTURE.md](PAYMENT-ARCHITECTURE.md). This file focuses on adapter extension and IBSng provisioning lifecycle.

## Payment adapters

PaymentManager is the single registry and dispatcher for payment modules. No provider is selected on a fresh install; an empty payment_provider setting means payment is disabled. Each adapter implements PaymentGateway; its optional configurationFields() metadata drives the admin settings UI and validation. Provider-specific values are stored as payment_<provider-code>_<field-key> and passed generically to the adapter.

Adapters are auto-discovered from app/Payments/gateways/*.php. To add a gateway, add one PHP adapter file in that directory, implement PaymentGateway (including `supportedCurrencies()`), and ensure the adapter's `code()` matches its provider code. The declared currencies drive admin configuration validation and are checked again before a payment transaction is created, so an unsupported currency fails before an external gateway request. The admin's per-gateway currency selector is rendered from that same capability list: fiat (IRR/IRT) and/or USDT options appear only when the adapter declares support. The administrator still chooses the active mode for that gateway; the mode is not inferred from a customer request. PaymentManager loads trusted adapter modules and the admin settings page obtains available provider codes and configuration fields from that same registry. No edits to PaymentManager, PaymentFlow, payment-callback.php, or a separate provider list should be needed. The optional registerGateway() method remains available for trusted programmatic registration/tests, not the normal extension path.

Keep provider secrets server-side and never trust callback values as payment proof. Fiat and USDT amounts are both captured on the order before payment initiation; the USDT snapshot is stored in `orders.price_usdt_snapshot` and is never re-read from the mutable product row during payment creation or verification. Fresh installs get this field from `database/schema.sql`; existing installs must apply `database/migrations/2026-11-02-order-usdt-price-snapshot.sql`. Legacy orders remain NULL because their historic crypto price cannot be inferred safely; crypto initiation for such orders fails closed. Adapter-level tests and CI are required; runtime credentials and live gateway sandbox checks remain deployment verification tasks.

## IBSng provisioning

Payment verification queues one create attempt per captured order destination. After the payment transaction commits, the callback performs a best-effort synchronous dispatch of queued create attempts. The admin dashboard links to admin/provisioning.php as a recovery/reconciliation surface for attempts that remain queued, become needs_review, or are left running after an interrupted request; this is not a background worker.

The dispatcher locks and claims the queue item as running before remote activity. It first looks up the requested username. If it already exists, it reconciles only when both its group and retrievable credentials match the immutable order snapshot; any mismatch or unreadable credential result becomes needs_review. A new create is sent at most once by this dispatcher. If the remote response or subsequent confirmation is ambiguous, the attempt becomes needs_review and is not made available for direct retry. A stale running attempt is likewise not automatically retried, because the remote operation may have committed before the process stopped.

The queue's idempotency key is scoped to order/server/create. Multi-server results remain independent; successful destinations are not re-run when another destination is unresolved. Each confirmed destination is also persisted in `subscriptions` with server-scoped username/remote identity and active state; expiry and quota stay unknown until a real IBSng synchronization supplies them. The provisioning recovery page is explicitly included in the router allowlist. The admin page permits an operator to record a manual succeeded/failed outcome for a needs_review or stale running attempt only after inspecting IBSng; this action does not send another remote request and requires an audit note. There is no automatic retry or refund. A verified payment callback may make one immediate dispatch attempt for each queued destination; this is a bounded request-time action, not a scheduled worker. Payment remains confirmed even when provisioning needs review.

The IBSng behavior is based on the tested reference repository; the Store's integration must preserve that behavior. CI syntax/contract checks do not replace the reference implementation's established test coverage.


## Customer order status

The verified browser payment result links to the customer-facing `order-status.php` page using the order's 32-character random public ID as a capability-style tracking reference. The page shows overall order state and independent provisioning results after payment confirmation. A confirmed successful destination may show the purchased account username and its order-snapshot password (inside a collapsed reveal section); pending or unsuccessful destinations do not reveal credentials. Raw IBSng diagnostics and buyer contact details are not exposed. The optional `ibsng_servers.service_name` is customer-facing: when non-empty it is displayed for that destination, and when empty no server/service heading is rendered. The internal server name, host, port, and admin credentials are never customer-facing. Treat the tracking URL as private and share it only with the purchaser. This page is not a customer login.
